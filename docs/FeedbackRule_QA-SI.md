## Choose the right channel

| Type | Use it for |
| :--- | :--- |
| Bug report | Server or official website accessibility, functionality, and gameplay bugs. Severe functional failures without security implications also belong here. |
| Question / clarification | Questions about how a server system or feature works. |
| Feature request | A concrete improvement, such as adding a way to view another player's latency with `/ping`. |
| Security report | Vulnerabilities or issues that could be exploited. Use the private reporting route below. |
| Rule wording or translation | Discrepancies or ambiguity in any language version, including English. Use the private reporting route below and identify the passage. |

On the [Security page](https://github.com/SchemaFoxLabs/NetherMC/security), select **Report a vulnerability**. If the option is unavailable, open an issue asking only for a private contact method. Do not include vulnerability details, exploit steps, or sensitive evidence in that public request.

Use in-game reporting first for routine, detectable cheating. GitHub feedback is not an immediate moderation channel.

Player reports while staff are offline and appeals of mistaken Join Blocks, Feature Blocks, or SubServer Blocks belong in [NetherMC-PublicReport](https://github.com/Labs-mcdev/NetherMC-PublicReport/). Read that repository's reporting instructions before submitting. Player reports require a valid in-game Report-ID.

## Supporter rewards

Verified serious vulnerability, bug, or security reports that meet the reward criteria earn a Support Rank with long-term validity and public contributor recognition. The contributor list may move to a separate document if it becomes too long.

Eligibility is verified by staff. Submission or acceptance alone does not earn a reward. These are non-purchase contribution rewards and are not tied to future financial contributions.

Your rank will be upgraded based on the value and number of your reports: **Support → SupportX → BugFinder → IssueExpert**. Continue to use the private security reporting route for vulnerabilities; rewards do not require public disclosure.

## Report quality

> [!IMPORTANT]
> Describe the issue, question, or request clearly enough for staff and other readers to understand it without guessing.

Describe a concrete, genuine problem or need. Unsupported subjective assessments and reports without substantive information are not accepted.

For a bug, include:

- The affected server or website feature.
- What happened and what you expected instead.
- Steps to reproduce the issue, or what you were doing when it occurred. If it cannot be reproduced reliably, say so and describe what you observed.

Client versions, relevant environment details, redacted logs, and screenshots can help. Your suspected cause and suggested solution are optional; you do not need to diagnose a bug before reporting it.

For a question, identify the system or feature and explain what is unclear and the relevant context. For a feature request, describe the need and the behavior you would like to see. Alternatives and supporting material are optional.

Feature requests are reviewed for necessity, feasibility, development scheduling, and compatibility with the current architecture. Review and implementation depend on these assessments and may take additional time.

## Handling capacity

Staff review submissions as time and available evidence allow. Some reports may remain pending for an extended period.

The usual 1–7 days, or 8–30 days during busy periods, are reference estimates for initial handling or a first reply only and may be exceeded, especially for feature requests. They are not deadlines for investigation, resolution, or sanctions.

For consultation before submitting supplementary material only: `mc-contact@schemafoxlabs.com`. Ask about a suitable submission method before sending private account details or sensitive evidence. The mailbox may be unable to receive attachments larger than **20 MiB**; first ask in a text-only message about larger material.

## Privacy and public information

> [!WARNING]
> Issues are public. Do not submit real names, personal contact details, identifying information, or images revealing anyone's real-world location. Remove private information and credentials from logs and screenshots before sharing them.

Check accuracy before publishing. Editing and deletion depend on GitHub permissions and repository or organization settings; they are not restricted solely to the original author. Do not assume a report can be completely withdrawn after publication, since others may already have seen or copied it.
